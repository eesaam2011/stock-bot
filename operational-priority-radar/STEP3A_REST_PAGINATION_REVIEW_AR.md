# OPR Step 3A — تدقيق ترقيم صفحات Alpaca REST

**الحالة: تنفيذ في مسار الاسترجاع الفعلي، مع استمرار حظر LIVE_TRUSTED والنشر.**

- أصبح استرجاع REST للكون يستخدم `native_recovery_batch_audited` لشموع `1Min` و`5Min` الأصلية بشكل مستقل، ويشترط وصول كل سلسلة إلى الصفحة النهائية. تُسجّل أعداد الصفحات والصفوف والرموز التي لم تظهر لها شموع في كل دفعة.
- حدود افتراضية لكل طلب: 64 صفحة، و100,000 صف، و200 رمز للدفعة، و8 عمّال كحد أعلى. أي تجاوز يوقف الاسترجاع دون منح الثقة. رفضنا كذلك رموز الاستجابة غير المطلوبة، بنية الصفحات الفاسدة، رموز الصفحة المتكررة أو غير الصالحة، والرموز المكررة في الطلب.
- `ProductionStartupRecovery.run()` يستخدم النسخة المدققة عندما يدعمها مصدر REST، ويرفض عدم اكتمال سلسلة الصفحات. الاختبارات القديمة التي تحقن قارئًا مبسطًا ما زالت مدعومة لكن لا تحصل على ادعاء باكتمال الترقيم.
- **الفارق الحاسم:** وصول API إلى آخر صفحة لا يثبت تغطية جلسة السوق؛ السهم غير السائل قد لا ينتج شمعة كل دقيقة. `full_session_coverage_proven=false` و`continuity_verified=False` باقية عمدًا.
- أُضيفت 12 حالة اختبار للتكرار، حد الصفحات والصفوف، الاستجابات المشوهة، أصل `5Min`، وتكامل مسار الاسترجاع الإنتاجي.

## المتبقي قبل Shadow الحقيقي

1. إثبات تغطية الجلسة ومصدر التاريخ وتحديد أول E/B في الجلسة، ثم كتابة الحالة الصحيحة إلى Redis مع fencing.
2. تسوية الصفقات النشطة وحالات halt بالترتيب الزمني، واستيعاب رسائل SIP الجديدة أثناء DRAINING ثم DIRECT بلا فقد.
3. اختبار Alpaca SIP 407 على اتصال فعلي تحت حمل السوق. نجاح Redis 7 وCI لا يثبت ذلك.

**الحزمة المرفوعة من GitHub Actions تتضمن نسخة الكود المطابقة للتشغيل و`pytest-q-output.txt` و`redis-integration-output.txt`. لا دمج main ولا نشر Render.**
