# Step 3J — بدء DRAINING بعد REST تلقائيًا، للمراجعة فقط

أصبح مسار `ProductionStartupRecovery` يدعم خيارًا **معطّلًا افتراضيًا**: `auto_begin_capture_drain=True` مع `audit_session_overlap=True`. يبدأ REST بينما SIP في حالة CAPTURING، ثم بعد انتهاء استرجاع REST وتدقيق ترتيب الشموع يفحص العصر وعدم وجود ACK سابق، ويستدعي `begin_drain(epoch)` قبل معاينة E/B المدمجة. بهذا لا نحتاج إلى بدء DRAINING يدويًا **قبل** REST، ولا تُفقد رسائل SIP التي وصلت أثناء الاسترجاع.

هذه ليست مرحلة تشغيل مباشر: يستمر استقبال SIP أثناء DRAINING، وتبقى الرسائل كلها محفوظة. لا `ack_batch`، ولا `finish_direct`، ولا `LIVE_TRUSTED`، ولا كتابة E/B. فشل REST يبقي الالتقاط في CAPTURING، وانقطاع 407 أو overflow يُبطل العصر. أضفنا فحصًا بعد عودة معاينة REST/SIP مباشرة، وفحصًا قبل إصدار تقرير المراجعة، حتى لا تمر إضافة رسالة أو 407 في النافذة بين المراجعة والتقرير.

**قيود باقية:** الالتقاط محدود بـ4096 رسالة/8MiB افتراضيًا، وقد يفيض خلال REST طويل؛ الفيض يؤدي إلى إبطال العصر لا إسقاط الرسائل القديمة. نتيجة REST+SIP لا تثبت اكتمال تغطية السوق أو تاريخ التوقفات. ولا يزال يلزم تنسيق حفظ E/B في Redis مع القيادة، وتسوية الصفقات، والتحقق من عدم فقد بيانات SIP، والتسليم الصفري إلى DIRECT، واختبار 407 الحقيقي في جلسة سوق.

10 اختبارات جديدة تشمل وصول رسالة أثناء REST، و407 أثناء REST وبعد المعاينة، والفيض، وفشل REST، وبدء DRAINING المسبق، والسباق بعد المعاينة، والإلغاء. CI يرفق `pytest -q` و18 اختبار Redis 7 الحقيقي. PR مسودة، دون دمج أو نشر.
