# OPR Step 3D — كتابة نتيجة استرجاع الصفقة كاملة في Redis بعملية واحدة

**نطاق الإصلاح:** استرجاع الصفقة النشطة بعد انقطاع البيانات. لا يغير معايير الاستراتيجية ولا يسمح بدخول بأثر رجعي ولا يمنح ثقة LIVE_TRUSTED.

## مشكلة فعلية بعد Step 3C
كان Step 3C يفحص ترتيب كل الأحداث قبل أول كتابة، لكنه ينفّذ بعدها انتقال T1 وSTOP/T2 بعمليات Lua منفصلة. إذا فقدت العملية القيادة أو حدث تعارض Redis بين العمليتين، قد تبقى T1 مسجلة دون النتيجة اللاحقة رغم أن السجل التاريخي سبق أن كشف النتيجة النهائية.

## التنفيذ
- أصبح `ActiveTradeChronologicalReconciler.reconcile` يكوّن مسار الانتقالات الكامل في الذاكرة بعد فحص الغموض، ولا يكتب أي حالة وسيطة.
- `ATOMIC_TRADE_RECOVERY_LUA` يتحقق داخل Redis من المالك والجيل والحالة المتوقعة للصفقة **وجميع** مفاتيح outbox أولًا، ثم يكتب حالة الصفقة النهائية وكل رسائل T1/STOP/T2/FINAL في عملية واحدة. أي تعارض أو فقدان قيادة يمنع جميع الكتابات.
- الحد الأقصى 4 أحداث outbox في الاسترجاع الواحد. إذا تجاوزت الأحداث الحد، يفشل الاسترجاع بدل تجزئة معاملة غير آمنة. يُرفض تكرار معرف حدث أو اختلاف جيل الحمولة قبل استدعاء Redis.
- تظل سجلات outbox تمثل الأحداث التاريخية المرصودة، ولا تُمثّل أسعار تنفيذ حقيقية. انتقال T1 الوسيط محفوظ كحدث outbox، والحالة النهائية وحدها تصبح مرئية في سجل الصفقة.
- ما زال فحص الترقيم لكل من شريط الصفقات و`native 1Min` وفحص ترتيب الأحداث المتزامنة إلزاميين قبل المعاملة.

## حدود الإثبات
- **نجاح معاملة Redis لا يثبت اكتمال صفقات SIP التاريخية ولا تسلسل أحداث halt**. قد ينقص REST حدث لم يبلّغ به المصدر؛ لا يُستنتج عكس ذلك من نجاح الترقيم.
- ما زالت إعادة بناء E/B الكاملة، وحفظها سببيًا، ودمج SIP وتسليم DIRECT واختبار 407 الحقيقي متبقية. `continuity_verified=False` و`gap_recovered=False` محفوظتان.
- اختبارات Redis الحقيقية في GitHub Actions تستخدم خدمة `redis:7-alpine` محلية بقاعدة اختبار `/15`؛ لا تستخدم Redis الإنتاجي.

**التسليم:** الحزمة الكاملة مع `pytest-q-output.txt` و`redis-integration-output.txt` و`REVIEW_MANIFEST.txt` عبر GitHub Actions. لا دمج main ولا نشر Render.
