نشر IPR_DIRECT_R1 والتراجع — يقوم به المستخدم، ولم يُنفذ هنا

1. فك ZIP وتحقق من SHA256SUMS.txt، واحتفظ بنسخة من ZIP وبصمته. لا تضع ملف أسرار داخل المجلد.
2. ارفع محتويات الحزمة تحت مجلد ipr-direct في فرع جديد اسمه ipr-direct-r1 بمستودع eesaam2011/stock-bot. لا main ولا خدمة Phase2 ولا بوت الأخبار/الفلوت. يمكن استخدام GitHub UI، أو الأوامر التالية من مجلد عمل جديد يوجد فيه IPR_DIRECT_R1.zip:

git clone https://github.com/eesaam2011/stock-bot.git
git -C stock-bot checkout -b ipr-direct-r1
unzip IPR_DIRECT_R1.zip -d stock-bot/ipr-direct
git -C stock-bot add ipr-direct
git -C stock-bot commit -m "Add IPR direct alerts R1"
git -C stock-bot push -u origin ipr-direct-r1

تسجيل الدخول يتم بالطريقة المعتادة للمستخدم؛ لا يكتب توكن Git في الأمر. إذا كان الفرع موجودًا مسبقًا لا force-push؛ استخدم نسخته التي تحققت منها أو توقف عن هذا الإجراء لتفادي الكتابة فوق عمل آخر.

3. أنشئ خدمة Render جديدة:
Name: ipr-direct-alerts
Type: Background Worker
Repository: eesaam2011/stock-bot
Branch: ipr-direct-r1
Root Directory: ipr-direct
Build: pip install -r requirements.txt
Start: python -m ipr.main
Auto-Deploy: Off
Instances: 1
Resources: 512Mi و0.5CPU، دون ترقية.

4. ضع متغيرات ENVIRONMENT_AR.txt قبل إنشاء/بدء الخدمة. قيم الأسرار من حساباتك فقط. لا ترسلها لي. يلزم Redis نفسه الذي تختاره لحفظ حالات IPR على اتصال native، وUpstash REST لقراءة الأخبار كما البوت المنتج؛ لا نفترض أنهما قاعدة واحدة. فعّل SIP بالمفاتيح المخولة؛ لا fallback إلى IEX.
5. النشر الأول سيبدأ البوت مباشرة عندما تسمح بيانات الجلسة؛ لا shadow ولا ملف موافقة ولا رسالة اختبار مطلوبة. لا Deploy متكرر أثناء الإقلاع. راقب Logs من البداية. لا تبدأ نسخة ثانية ترسل إلى الوجهة نفسها.
6. اقرأ الإصدار/الفرع والموارد وBuild/Start ومصدر السجلات. علامات التقدم: GUARD_BOOT_CLAIMED، IPR_SESSION_SOURCES، PREP_PROGRESS ثم PREP_READY، IPR_SCAN وIPR_METRICS. لا تتوقع رسالة لمجرد بدء البوت؛ الرسالة تحتاج شروط E/B/confluence/ENTRY الأصلية، والثقة بعد ACK والتاريخ والاستمرارية.
7. أول بناء لمخزون20جلسة قد يكون طويلًا. لا أزعم أنه يكتمل قبل الافتتاح إذا نشرته قبله بدقائق. ابدأ قبل الجلسة بوقت واسع، أو قبل يوم التداول. إذا لم يكتمل فلا ترشيحات جديدة، وتبقى متابعة الحالات القائمة من البث/الاستعادة متاحة بقدر سلامة المصدر. تجنب سلسلة restarts لأنها تستهلك ميزانية4إقلاعات لليوم UTC.
8. خارج جلسة التداول يوقف الاكتشاف فقط، ويبقى الحارس والمتابعة. ينتقل تلقائيًا إلى يوم جديد وتقويم جديد؛ لا حاجة Resume يومي إذا بقيت الخدمة تعمل. Suspend يدوي يعني توقف الكل حتى يستأنفها المستخدم.

التراجع
- عند خلل أو موارد غير مقبولة: اضغط Suspend للخدمة الجديدة فقط، وسجل وقت الإيقاف، واحفظ Logs وMetrics قبل ضياعها.
- لا تحذف Redis أو telegram ledger ولا تغير namespace ipr_direct:v1؛ لا تمسح ميزانية الإقلاعات لإجبار إعادة التشغيل.
- إذا عندك إصدار سابق متوافق من IPR_DIRECT يستخدم namespace نفسه، ارجع إلى commit ذلك الإصدار ثم انشره بعد التأكد من توقف القديم. لا تشغيل نسختين معًا.
- في أول إصدار لا يوجد سابق متوافق لهذه النسخة؛ التراجع الآمن هو إبقاء الخدمة الجديدة موقوفة ومتابعة الحالات التي نُبّهت عليها يدويًا. لا تدّع أن خدمة IPR القديمة أو Phase2 ستستعيد حالات النسخة الجديدة تلقائيًا.
- حزم D القديمة والموصلات الأصلية لم تُعدّل. لا توجد هجرة تلقائية لحالات خدمات سابقة إلى namespace الجديد. حماية O/A/U/R تشمل ما تنشئه هذه النسخة وتستعيده من سجلها، لا ما لم يُنقل إليها أصلًا.
